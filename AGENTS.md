# AGENTS.md

Инструкции для ИИ-агентов (Claude Code, Codex, Gemini и др.) и людей, работающих в репозитории.

## Проект

«Пульт шамана» — RnD-проект курса ВРМП (НГУ ФИТ, 2026). Android-игра «Охота на духов»
с непривычным управлением + исследование: окупается ли усложнение распознавания жестов
(пороги vs DTW vs камера MediaPipe) по сравнению с тачем.

Перед работой прочитай:
- [docs/SPEC.md](docs/SPEC.md) — игра, команды, датчики, режимы.
- [docs/stage2-3/TZ.md](docs/stage2-3/TZ.md) — сценарии, макеты и техническое проектирование.
- [docs/RESEARCH.md](docs/RESEARCH.md) — гипотезы, бенчмарк, пользовательский тест, метрики.
- [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — модули, интерфейсы, формат записей.
- [docs/ROADMAP.md](docs/ROADMAP.md) — роли, этапы, критерии приёмки.
- [docs/DECISIONS.md](docs/DECISIONS.md) — принятые решения. Не пересматривай их молча.

## Команды

```bash
./gradlew :core:test            # юнит-тесты ядра — запускай после любых изменений в core/
./gradlew :bench:run --args=""  # офлайн-бенчмарк
./gradlew :app:assembleDebug    # сборка APK
cd analysis && python -m pip install -r requirements.txt
```

Gradle-сборка тяжёлая: не запускай несколько сборок параллельно, предпочитай `:core:test` полной сборке.

## Правила

1. **Ядро без Android.** В `core/` нельзя импортировать `android.*`. Всё, что влияет на распознавание
   и правила игры, — в `core/`, чтобы бенчмарк проверял тот же код, что на телефоне.
2. **Детерминизм.** Распознаватели и игровая логика используют только время из кадров (`tNanos`)
   и сиды. Никаких `System.currentTimeMillis()`, `Random()` без сида, глобального состояния.
3. **Общий интерфейс.** Новый способ ввода = новая реализация `GestureRecognizer`; игра и арбитр
   не знают, какой распознаватель активен.
4. **TDD обязателен** — см. раздел «Разработка через тесты (TDD)» ниже. Тесты для распознавателей
   и `CommandArbiter` — на синтетических или сэмпловых записях (`data/samples/`).
5. **Формат записей** (см. ARCHITECTURE.md) меняется только с версионированием в `meta.json`
   и обновлением `:bench` и `analysis/`.
6. **Приватность.** Никаких имён участников в данных и коммитах — только `P01`…`P12`.
   Папка `context/` (материалы курса, переписка) в `.gitignore`, не коммить её и не цитируй в репозитории.
7. **Язык.** Документация и коммиты — на русском; идентификаторы и комментарии в коде — на английском.
8. **Решения.** Если задача требует изменить решение из DECISIONS.md — сначала спроси, затем добавь новую запись.
9. **Документация живая.** Документация растёт вместе с проектом и не должна устаревать — см. раздел ниже.

## Разработка через тесты (TDD)

По мотивам скилла `test-driven-development` из [obra/superpowers](https://github.com/obra/superpowers) (MIT).
Применяется к любой новой функции, исправлению бага, рефакторингу и изменению поведения.

**Железное правило: нет продакшен-кода без падающего теста.** Написал код до теста — удали и начни с теста.

Цикл **Red → Green → Refactor**:
1. **Red.** Один минимальный тест на одно поведение, понятное имя, реальный код (моки — только если без них никак).
2. **Убедись, что тест падает** (`./gradlew :core:test --tests '<Class>'`) — именно из-за отсутствующей
   функциональности, а не из-за опечатки или ошибки компиляции. Прошёл сразу — тест проверяет не то.
3. **Green.** Минимальный код, чтобы тест прошёл. Без «заодно» и лишних параметров.
4. **Убедись, что проходит весь набор** (`./gradlew :core:test`), вывод чистый, без ошибок и предупреждений.
   Любой упавший тест, даже не твой, — упомяни в отчёте.
5. **Refactor.** Только при зелёных тестах: убрать дублирование, улучшить имена. Поведение не добавлять.

Хорошие тесты:
- Перед написанием назови изменение в коде, которое этот тест поймает. Не можешь — тест не нужен или проверяет не то.
- Ожидаемые значения — литералы и посчитанные вручную данные, а не результат того же кода.
- Проверяй поведение, а не мок и не значение констант.
- Код, нужный только тестам, — в тестовых утилитах, не в продакшен-классах.
- Баг → сначала тест, воспроизводящий его, потом исправление.

Исключения (одноразовый прототип, сгенерированный код, конфигурация, чистый UI без логики) — только по согласованию с человеком.

## Актуальность документации

Документация — часть изменения, а не отдельная задача «на потом». Каждый агент и человек,
меняя проект, **в том же PR** приводит документы в соответствие с кодом:

| Что изменилось | Что обновить |
|---|---|
| Модули, интерфейсы `:core`, поток данных, формат записей | `docs/ARCHITECTURE.md` |
| Игровые правила, команды, жесты, датчики, экраны, режимы | `docs/SPEC.md` |
| Гипотезы, метрики, протокол, анализ | `docs/RESEARCH.md` |
| Принятое или пересмотренное решение | новая строка в `docs/DECISIONS.md` |
| Роли, этапы, сроки, критерии приёмки | `docs/ROADMAP.md` |
| Команды сборки, структура репозитория, правила работы | `AGENTS.md`, `README.md` |
| Зависимости и их версии | `gradle/libs.versions.toml` + причина в `DECISIONS.md`, если это не рутинное обновление |

Правила:
- **Перед началом работы** прочитай документы, относящиеся к задаче. Если видишь расхождение
  документации и кода — исправь его (или заведи issue, если исправление не по теме задачи), не обходи молча.
- **Перед завершением** проверь: всё, что ты изменил, отражено в документах; ссылки, пути, имена
  классов и команды в документах существуют и работают. PR без нужного обновления документации не готов к ревью.
- Пиши о **текущем** состоянии. Устаревшее удаляй или переписывай, а не дописывай «UPD» поверх.
  Историю хранит git и `DECISIONS.md`.
- Новая заметная подсистема (например, распознаватель, режим, экран) — новый раздел в соответствующем
  документе; новый большой документ — ссылка на него из `README.md` и `AGENTS.md`.
- Не дублируй: один факт — в одном месте, остальные документы ссылаются на него.

## Процесс

- Задачи — issues в GitHub, [канбан-доска](https://github.com/users/Denmurzik/projects/1) в GitHub Projects (Backlog → Todo → In Progress → Review → Done).
- Ветка на задачу: `<area>/<issue>-<short-name>`, например `core/12-dtw`.
- PR ссылается на issue (`Closes #12`), ревью — минимум один человек из другой зоны.
- Коммиты: `<область>: <что сделано>` на русском, например `core: DTW с полосой Сакое–Чиба`.
- Метки областей: `area:core`, `area:bench`, `area:sensors`, `area:game`, `area:camera`, `area:research`, `area:docs`.

## UI: Material 3 Expressive

Дизайн-язык — **Material 3 Expressive** (D-16). Правила для UI-кода в `app/`:

- Корневая тема — `MaterialExpressiveTheme(motionScheme = MotionScheme.expressive())`, цвета — из
  схемы проекта (`expressiveLightColorScheme` / тёмная схема), не хардкодить цвета и размеры в экранах.
- Версия `material3` закреплена в `gradle/libs.versions.toml` (1.5.x): Compose BOM 2026.09 тянет 1.4.0 без Expressive API.
  Не удаляй override, пока BOM не подтянет 1.5.0+.
- Стабильно в 1.5.0: `MaterialExpressiveTheme`, `MotionScheme.expressive()`, `ButtonGroup`, `ToggleButton`,
  `SplitButton`, `FloatingToolbar`, FAB menu, flexible top app bars, wavy progress indicators.
  Ещё **экспериментально** (нужен `@OptIn(ExperimentalMaterial3ExpressiveApi::class)`):
  `LoadingIndicator`, `MaterialShapes` / shape morphing, `AppBarWithSearch`. Используй их точечно.
- Сверяй сигнатуры по актуальной документации, а не по памяти:
  context7 — library ID `/websites/developer_android_reference_kotlin_androidx_compose_material3`.
- Рекомендуемые инструменты для агентов:
  - скилл [hamen/material-3-skill](https://github.com/hamen/material-3-skill) — токены, компоненты, аудит соответствия M3;
  - [Google Design MCP](https://developers.google.com/design-mcp/overview) (`https://design.googleapis.com/mcp`) —
    генерация цветовой схемы, иконки, шрифты.
- Дизайн-система и макеты экранов — в Figma (см. задачи этапа 2–3); код следует макетам.
