# Исследование

## Вопрос

**Окупается ли усложнение распознавания жестов?** Сравниваем три распознавателя за одним
интерфейсом — пороговые правила по IMU, DTW по эталонам IMU и жесты рукой через камеру
(MediaPipe Hand Landmarker) — по точности, ложным срабатываниям, устойчивости к скорости
жеста и задержке, а затем на людях против обычного тач-управления.

Отрицательный результат допустим (согласовано с преподавателем): если сложный алгоритм
не даёт заметного выигрыша, ценность — в корректном эксперименте и объяснении.

## Гипотезы

- **H1.** На простом жесте (рывок) пороги не хуже DTW по F1 и быстрее по задержке.
- **H2.** На траекторном жесте (круг) DTW даёт F1 выше порогов, особенно при изменении скорости.
- **H3.** Персональные эталоны (из калибровки) дают DTW выше точность, чем общие эталоны.
- **H4.** Камера даёт меньше ложных срабатываний при движении телефона, но больше пропусков
  (потеря руки из кадра, освещение) и большую задержку.
- **H5.** Тач быстрее и точнее для новичков, но разрыв сокращается к концу сессии (скорость обучения).

## Часть 1. Офлайн-бенчмарк на записях

**Датасет**: ≥ 8 человек × 3 жеста × 3 скорости (медленно/нормально/быстро) × 10 повторов
+ нулевые записи (ходьба, взять со стола, убрать в карман, печать) ≥ 5 мин на человека.
IMU и камера пишутся одновременно. Формат — [ARCHITECTURE.md](ARCHITECTURE.md#формат-записей).

**Протокол**:
- Все распознаватели прогоняются через `:bench` — тот же Kotlin-код, что на телефоне, на JVM.
- Потоковый прогон (а не по заранее нарезанным сегментам): распознаватель сам ищет начало и конец.
- DTW в двух режимах: *персональный* (эталоны — первые 5 повторов человека, тест — остальные)
  и *общий* (leave-one-subject-out: эталоны всех, кроме тестируемого).
- Параметрические прогоны: порог/гистерезис/мин. длительность (пороги); ширина полосы Сакое–Чиба,
  набор признаков, порог отказа, число эталонов (DTW); порог сжатия кулака, окно траектории (камера).

**Метрики**: precision / recall / F1 по классам, матрица ошибок, ложные срабатывания в минуту
на нулевом потоке, F1 в зависимости от скорости жеста, задержка (конец жеста → событие),
время CPU на кадр (на JVM и на устройстве).

## Часть 2. Пользовательский тест

Порядок условий, сиды, инструкции участнику и формы — в [PROTOCOL.md](PROTOCOL.md).

- **Участники**: 12 человек (не из команды), анонимные ID `P01`–`P12`.
- **Дизайн**: внутрисубъектный, 4 условия — **Тач / Пороги / DTW / Камера**,
  порядок по сбалансированному латинскому квадрату (Williams, 4×4, повторить 3 раза).
- **Сессия** ≈ 20–25 мин: инструктаж → калибровка → для каждого условия 1 мин тренировки + 3 мин
  задания → анкета после условия → итоговое интервью.
- **Задания**: 4 эквивалентных сида (одинаковое число и типы духов), сид привязан к позиции,
  а не к условию. Доп. события отключены.
- **Условия среды**: одна комната, фиксированное освещение, один и тот же телефон.

**Метрики**:
- время на духа (от появления до успешной команды), доля успешных;
- ошибки: неверная команда, промах (дух вне конуса), пропуск (дух ушёл);
- ложные срабатывания: команда без намерения (нет духа в конусе и отменена / отмечена участником);
- число отмен;
- кривая обучения: время на духа по порядковому номеру духа внутри условия;
- задержка «конец жеста → отклик» из лога;
- субъективно: raw NASA-TLX + 3 вопроса по шкале 1–7 (удобство, контроль, усталость) + комментарии.
  Впечатления сопоставляем с объективными метриками.

**Анализ** (n = 12, без предположения нормальности): критерий Фридмана по условию, пост-хок
Уилкоксона с поправкой Холма, размеры эффекта; проверка эффекта порядка. Python: pandas, scipy,
matplotlib в `analysis/`. Входные данные и запуск описаны в [инструкции анализа](../analysis/README.md).

## Что не делаем

- Замер энергопотребления (решено не включать).
- Распознавание речи (микрофон — только уровень громкости).
